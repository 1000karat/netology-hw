### Задание 1

### Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования.

Необходимо описать, какие варианты резервного копирования подходят в случаях:

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

*Приведите ответ в свободной форме.*

#### 🔧 Решение
**1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день**  
Для такого случая подходит полное резервное копирование (Full Backup).  

**Как работает:** Один раз в сутки создаётся полная копия базы данных. В резервной копии содержатся все данные на момент создания бэкапа.   
**Пример:** Полный бэкап выполняется каждый день в 00:00. Если база данных выйдет из строя днём, можно восстановить состояние базы на начало текущего дня.

**Преимущества:**  
- простое восстановление;
- высокая надёжность;
- не требуется цепочка нескольких бэкапов.  

**Недостатки:**
- требует много места;
- долгое время создания копии для больших БД.


**1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.**  
Для этого подходит **инкрементное резервное копирование**, или **Point-in-Time Recovery (PITR)** с использованием журналов транзакций.
**Как работает:** Создаётся полный бэкап. Затем регулярно сохраняются изменения:
- бинарные логи;
- WAL-журналы;
- transaction logs.

**Пример:** 
- полный бэкап создаётся ночью;
- журналы транзакций сохраняются каждые 5–10 минут;
- при аварии можно восстановить базу на конкретное время, например за час до сбоя.

**Преимущества:** 
- минимальная потеря данных;
- возможность восстановления на определённый момент времени.

**Недостатки:** 
- более сложное администрирование;
- необходимо хранить и контролировать журналы транзакций.


**1.3.\* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.**
Да, такой кейс возможен. Для этого используются:
- репликация;
- отказоустойчивые кластеры;
- механизмы Failover.

**Как это работает:** 
- есть основная база данных (Master/Primary);
- есть одна или несколько резервных реплик (Replica/Standby);
- данные между ними синхронизируются почти в реальном времени.

**Если основная база выходит из строя:**
- система автоматически переключает нагрузку на резервную БД;
- пользователи продолжают работать практически без перерыва.

**Преимущества:**
- высокая доступность сервиса;
- минимальный простой;
- возможность обслуживания без остановки системы.

**Недостатки:**
- сложность настройки;
- более высокие требования к инфраструктуре;
- возможна потеря нескольких последних транзакций при асинхронной репликации.


### Задание 2

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

*Приведите ответ в свободной форме.*

#### 🔧 Решение

**2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).**

Для **создания SQL-дампа базы данных**, содержащей: структуру таблиц, данные, индексы, функции и другие объекты БД. Пример команды:

`pg_dump -U postgres -d test_db > test_db_backup.sql`

Для **восстановления базы данных** из SQL-файла резервной копии, пример команды: 

`psql -U postgres -d test_db < test_db_backup.sql` 

**Где:**
- `pg_dump` — утилита резервного копирования PostgreSQL;
- `-U postgres` — пользователь БД;
- `-d test_db` — имя базы данных;
- `test_db_backup.sql` — файл резервной копии.


**Использование формата custom и pg_restore**

Создание резервной копии: `pg_dump -U postgres -Fc test_db -f test_db.dump`  
Восстановление: `pg_restore -U postgres -d test_db test_db.dump`  

Преимущества формата custom:
- поддержка сжатия;
- более быстрое восстановление;
- возможность выборочного восстановления;
- поддержка параллельной загрузки.

**2.1.\* Возможно ли автоматизировать этот процесс? Если да, то как?**
Процесс резервного копирования и восстановления можно и нужно автоматизировать. С помощью:
- использование cron в Linux;
- Bash-скрипты;
- сторонние инструменты: pgBackRest, Barman.

### Задание 3
3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.

3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

*Приведите ответ в свободной форме.*

#### 🔧 Решение

**3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.**

В MySQL инкрементное резервное копирование обычно реализуется через бинарные журналы (binary logs). Включение binary log
Пример настройки в my.cnf:
```
[mysqld]
log_bin = /var/log/mysql/mysql-bin.log
server-id = 1
```

Создание полной резервной копии: `mysqldump -u root -p --all-databases --single-transaction --flush-logs --master-data=2 > full_backup.sql`  
Инкрементное резервное копирование через binary logs: `mysqlbinlog /var/log/mysql/mysql-bin.000001 > incremental_backup.sql`  
где:
- `mysqldump` — утилита для создания резервной копии MySQL;
- `-u root` — пользователь базы данных;
- `-p` — запрос пароля пользователя;
- `--all-databases` — резервное копирование всех баз данных;
- `--single-transaction` — создание консистентного бэкапа без блокировки таблиц;
- `--flush-logs` — создание нового binary log файла;
- `--master-data=2` — запись координат binary log в резервную копию;
- `>` — перенаправление вывода в файл;
- `full_backup.sql` — файл полной резервной копии.

Восстановление:  
Сначала восстанавливается полный бэкап: `mysql -u root -p < full_backup.sql`  
Затем применяются изменения из binary logs: `mysql -u root -p < incremental_backup.sql`


**3.1.\* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?**

1. При выходе из строя основной базы можно быстро переключиться на реплику.
2. Минимальная потеря данных. Реплика получает изменения практически в реальном времени.
3. Масштабирование нагрузки.
